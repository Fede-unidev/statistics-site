The toy ECC scheme: steps and role of the keys


The scheme is an ECIES/ElGamal-style hybrid on the real secp256k1 curve, with the private key restricted to a small range (here 16–32 bits instead of about 256). Keys. The private key k is a secret integer; the public key is the point Q = kG and can be published, because recovering k from Q is the Elliptic Curve Discrete Logarithm Problem. Encryption (needs only Q): (1) pick a fresh random ephemeral scalar r; (2) compute R = rG; (3) compute the shared point S = rQ; (4) derive a keystream from S, here Keccak-256(S.x ‖ counter); (5) XOR it with the message bytes to get c. The pair (R, c) is sent. Decryption (needs k): compute S = kR = k(rG) = r(kG) = rQ, regenerate the same keystream and XOR again. Anybody who sees only (Q, R, c) would have to solve a Diffie–Hellman problem to obtain S. The elliptic-curve part therefore only agrees on a secret; the bulk encryption is a stream cipher. (Mapping a message directly onto curve points is awkward and limited in length, which is why the hybrid design is used.)


Similarities and differences with the Caesar cipher


    

  • Procedure. Both are "add a secret stream and subtract it again". Caesar adds the same constant k (mod 26) to every letter; the ECC scheme XORs each byte with a different pseudo-random byte. Caesar is symmetric (same key to encrypt and decrypt) and deterministic; the ECC scheme is asymmetric (Q encrypts, k decrypts) and probabilistic: a fresh r gives a different ciphertext every time, while Caesar always gives the same one for the same message.
    • 

  • Key space. Caesar has 26 keys (about 4.7 bits). The toy ECC scheme has 2bits private keys, a number we choose; a properly configured one has about 2256 (≈ 128-bit security, because of generic square-root attacks).
    • 

  • Statistical properties. Caesar is a monoalphabetic substitution: the letter histogram is only rotated, so entropy and all frequency patterns of the language are preserved. This is exactly what the statistical attack exploits. The ECC-derived keystream is pseudo-random, so the ciphertext bytes look uniform (entropy close to 8 bits/byte in section 4) and carry no language statistics. Neither scheme has diffusion: changing one plaintext symbol changes only one ciphertext symbol, which also makes both malleable.
    • 



Statistical attack on the Caesar cipher: effectiveness and limits


Using a training corpus (Shakespeare, 90%) we build letter, bigram and trigram statistics, and test on a held-out 10% so the attack never sees its own test text. The attack tries all 26 keys and keeps the one whose decryption looks most like English according to a score. Measured accuracy (400 random keys and text windows per length, one run; it varies a little, run section 5 to reproduce):

Longer ciphertexts are easier because their histogram converges to the language distribution. Very short ones (under about 10 letters) are ambiguous: several shifts can give plausible text, and with 5 letters even the best method fails about one time in four. The simple "most frequent letter is E" heuristic is fragile because it depends on a single count, so it needs hundreds of letters; scoring all 26 candidates with the full distribution (chi², unigram log-likelihood) uses much more information. N-gram scoring is best, because it also uses letter order, so it needs the fewest letters. The "exhaustive search + common words" approach also works but needs longer text and, with word spaces removed, is less natural. Limitations: the attack assumes the language is known and the text is long enough and typical; a corpus of a different style or language (or text without the letter E, or with many names) shifts the statistics; and it only works because the cipher preserves the statistics of the plaintext.


Attack on the restricted private key and why it does not scale


Because k is below 2bits, Q = kG can be inverted. Exhaustive search computes G, 2G, 3G, … until it equals Q: O(2bits) point additions, with a trivial success test (no need to recognize the plaintext). Baby-step giant-step stores about 2bits/2 points jG and then walks Q − i·mG until it hits the table, so it needs only about 2bits/2 time and memory: in our tests a 32-bit key falls in seconds, while exhaustive search would take hours at about 105 additions per second in the browser. With the recovered k we compute S = kR and decrypt like the receiver.


Difference from the Caesar attack. The Caesar attack is ciphertext-only and statistical: it needs a model of the language and gets worse with short messages. The ECC attack is purely algebraic: it does not use the message statistics at all (the ciphertext looks random) and works identically for one byte or one megabyte, because it attacks the public key Q, and success is checked exactly by Q = kG. What both share is that the key space is searchable. Why it fails on a proper configuration: with k uniform in a group of order n ≈ 2256, exhaustive search needs about 1077 additions and baby-step giant-step (or Pollard's rho, which needs almost no memory) about 2128 ≈ 3·1038 operations, and no better generic classical attack is known for secp256k1. Even at one billion additions per second this is on the order of 1022 years for the square-root attacks; the page prints an estimate based on the speed measured on your machine. (A large quantum computer running Shor's algorithm would change this, which is outside the scope here.)


Weaknesses from the design of the toy scheme itself


    

  • Restricted key space (the main flaw). Everything above. A small ephemeral r would be just as bad: the attacker could recover r from R and compute S = rQ.
    • 

  • No authentication. The XOR stream makes ciphertexts malleable: flipping a ciphertext bit flips the same plaintext bit, and nobody notices. A real scheme adds a MAC or uses authenticated encryption.
    • 

  • Ephemeral-key reuse. Reusing r produces the same keystream, so the XOR of two ciphertexts equals the XOR of the two plaintexts.
    • 

  • Missing validation and metadata. The receiver should check that R is on the curve and not the point at infinity, and the ciphertext leaks the message length. The key derivation also has no domain separation (no context label).
    • 

  • Static receiver key. If k is ever compromised, all past messages can be decrypted, since every R is transmitted in clear; there is no forward secrecy for the receiver.
    • 



The first weakness comes from the restriction of the key range; the others would remain even with a full-size key.
