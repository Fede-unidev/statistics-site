4. Role of each primitive


BIP-39     mnemonic (encoding of entropy + checksum) → 512-bit seed via PBKDF2-HMAC-SHA512 (key stretching)
BIP-32     from the seed, a tree of HD keys via HMAC-SHA512 (key derivation, not generation)
BIP-44     standard path m/44'/coin'/account'/change/index (Ethereum: coin 60)
secp256k1  elliptic curve: public key = k·G (public-key crypto, signatures)
Keccak-256 hash of the public key; address = last 20 bytes
EIP-55     upper/lower case derived from the address hash = checksum (detects typos, does not protect)

Timeline: RSA 1977 · SHA-2 2001 · BIP-32 2012 · BIP-39 2013 · BIP-44 2014 · SHA-3 2015 · EIP-55 2016

Why several primitives: each step solves a different problem (key management, public/private relation and signatures,
hashing, error detection). No single algorithm does it all.

6. Discussion




Generation, derivation, public-key cryptography, hashing, checksum, encoding


    

  • Key generation vs key derivation. Generation creates new secret randomness: BIP-39 draws 128–256 bits of entropy from a cryptographically secure random generator. Derivation is a deterministic function of an existing secret: PBKDF2 turns the mnemonic into a 512-bit seed, and BIP-32 (HMAC-SHA512) turns the seed into a tree of keys. Derivation adds no entropy: the whole tree is exactly as secret as the original entropy (plus the optional passphrase). Its advantage is that a single backup recovers every key.
    • 

  • Public-key cryptography. secp256k1 links a private key k to a public key K = kG. Anyone can verify an ECDSA signature made with k, but only the holder of k can create one. This is the only step that provides ownership and authentication.
    • 

  • Hashing. Keccak-256 compresses the 64-byte public key into 32 bytes and the address keeps the last 20. It is a one-way, collision-resistant function with strong avalanche. In the pipeline, SHA-256 (BIP-39 checksum) and SHA-512 (PBKDF2 and HMAC) are used as well.
    • 

  • Checksum. Both BIP-39 (the last bits of the mnemonic come from SHA-256) and EIP-55 (letter case derived from the hash of the address) add redundancy to detect typing errors. About 15 of the 40 hex characters are letters on average, so EIP-55 gives roughly 15 bits of error detection: a random typo is caught with probability about 1 − 2−15. It provides no secrecy and no authentication.
    • 

  • Encoding. Mnemonic words (11 bits per word from a list of 2048), hexadecimal strings and mixed-case text are just reversible representations of the same bytes. They give readability, not security.
    • 



Why several primitives instead of one algorithm


Each step needs a different property. BIP-39/32/44 handle key management: one memorable backup, deterministic recovery and a standard layout (m/44'/60'/0'/0/0 for Ethereum accounts). secp256k1 provides the asymmetric relation between private and public keys and digital signatures, which hashes cannot provide. Keccak-256 provides a short, uniform, one-way identifier. EIP-55 provides cheap error detection without changing the address. Using one algorithm for everything would sacrifice one of these properties (a hash cannot sign, a signature scheme is not a compressing hash), and keeping the roles separate also limits damage if one primitive is weakened. Note that non-hardened BIP-32 derivation has a known caveat: an extended public key plus one child private key reveals the parent private key, which is why the Ethereum path hardens its upper levels.


Historical context


RSA (1977) introduced practical public-key cryptography. SHA-2 / SHA-512 followed in 2001, and BIP-32 (2012), BIP-39 (2013) and BIP-44 (2014) built wallet standards on top of Bitcoin, using HMAC-SHA512 and PBKDF2-SHA512. NIST standardized SHA-3 in 2015, based on Keccak, the winner of its hash competition. Ethereum adopted Keccak just before the final standard was published, and NIST then changed the padding (domain-separation suffix), so Ethereum's "Keccak-256" differs from the standardized SHA3-256: the same input gives different outputs (section 3). EIP-55 (2016) added the mixed-case checksum afterwards, without changing addresses.


SHA-2/SHA-512 vs Keccak/SHA-3


Both are cryptographic hash functions, but they are built differently. SHA-2 uses the Merkle–Damgård construction with a compression function (non-truncated SHA-256 and SHA-512 are vulnerable to length-extension attacks). Keccak uses a sponge construction on the 1600-bit permutation Keccak-f, with a rate/capacity split that avoids length extension. SHA3-256 and Keccak-256 share the same core and differ only in the padding/domain-separation bytes (0x06 in the standard, 0x01 in the original), which is enough to give completely different digests.


Statistical properties


A good hash has uniform-looking outputs and an avalanche effect of about 50% (our HW1 test shows this for Keccak-256). This makes the 160-bit address essentially uniform over its space, so collisions follow the birthday bound of about 280 trials, which is infeasible. Private keys must be uniformly random over a space of about 2256 values; a 12-word mnemonic carries 128 bits of entropy and a 24-word one 256 bits. The seed is 512 bits long, but its entropy is still at most that of the mnemonic (plus passphrase). By contrast, the relation between private and public key is algebraic (see HW1): it is not designed to look random, only to be hard to invert.
